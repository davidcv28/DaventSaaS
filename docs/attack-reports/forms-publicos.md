# Attack Report — Formularios públicos de tiendas

Fecha: 2026-11-13 · Backend local `http://localhost:8000` · Tiendas usadas: `mi-qa`, `olivium-qa`, `mt-qa`, `davent` · Cliente de prueba: `atk-a@test.com` (customer id 17). No se crearon registros de negocio durante las pruebas; las verificaciones de alta se hicieron con payloads inválidos, revisión de código y dos POST de contacto de auditoría.

## Resultado general

La superficie está bastante endurecida: captcha firmado + nonce de un solo uso, límites de longitud, validación de email CRLF, reviews limitadas a clientes autenticados, uploads públicos recodificados a WebP y mass-assignment bloqueado por serializers explícitos.

**Hallazgo prioritario:** los throttles de DRF identifican por el último `X-Forwarded-For` cuando `NUM_PROXIES=1`. En el entorno observado (devserver / request que llega con XFF ya completo) rotar ese header evade el límite `store_contact=10/h`. Además las reviews ya **no exigen captcha** y no tienen unicidad ni verificación de compra: con IPs distribuidas o varias cuentas puede inundarse la ficha y alterar el rating.

## Recomendaciones

1. **FP-01/FP-04**: corregir identidad del throttle según topología real:
   - en producción, exigir que el proxy/cdn **sobrescriba o agregue** el XFF real y calibrar `NUM_TRUSTED_PROXIES`;
   - para forms sensibles, combinar IP + cuenta (`customer_id` en reviews/orders) + fingerprint opcional;
   - ignorar `X-Forwarded-For` completo si el request no viene de proxy confiable.
2. **FP-02**: decidir política: si las reviews deben seguir requiriendo captcha, agregar `challenge_id`/`captcha_answer` + `verify_captcha` en `product_reviews`; si la autenticación reemplaza al captcha, actualizar comentarios/contrato y compensar con límites por cuenta.
3. **FP-03**: agregar `UniqueConstraint(store, product, customer)` o reemplazo idempotente (“actualizar mi opinión”), y si el negocio lo exige, requerir `OrderItem` comprado/entregado para ese `customer` o moderación previa.
4. **FP-05/FP-15**: defensa en profundidad: eliminar CR/LF y caracteres de control en `name`, escapar/normalizar HTML en contact/reviews y mantener prohibido `v-html` en paneles/emails.
5. **FP-06**: conservar el pipeline: todo upload público debe pasar `validate_image_file` + `normalize_image` + key UUID + URL privada; no aceptar nuevos `put_object` públicos sin ese camino.
